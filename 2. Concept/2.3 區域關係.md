# 2.3 區域關係

> 2.1 介紹了三個區域, 2.2 介紹了檔案狀態 <br>
> 這裡把兩者串起來: 區域之間怎麼流動、指令會動到哪裡

<br><br>


## 三個區塊的關係

```
工作目錄          暫存區              儲存庫 (.git)
(Working)   →   (Staging/Index)  →  (Repository)
   改檔案          git add              git commit
```

> 基本流程就三步: <br>
> 1. 在工作目錄修改檔案 <br>
> 2. `git add` 把要提交的變更加入暫存區 <br>
> 3. `git commit` 把暫存區寫入本地儲存庫 <br>
> 之後若要同步到 GitHub 等遠端, 再用 `git push`（見 2.5 GitHub）

<br><br>


## 指令會怎麼動到三個區塊

> **git add [file]** <br>
> 工作目錄的修改寫入暫存區; 同時會在 `.git/objects` 建立物件, 並更新 index 的索引

> **git commit** <br>
> 暫存區的內容寫入儲存庫, 目前分支(例如 main)會往前移動到這次提交

> **git status** <br>
> 告訴你: 哪些檔案改了還沒 add、哪些已 staged 還沒 commit

> **git diff** <br>
> 看工作目錄 vs 暫存區的差異

> **git diff --cached** <br>
> 看暫存區 vs 上一次 commit 的差異

> **git reset HEAD [file]** <br>
> 把檔案從暫存區移回工作目錄(取消 staged), **工作目錄的修改還在**

> **git rm --cached [file]** <br>
> 從暫存區移除追蹤, 工作目錄的檔案本身不變

> **git checkout -- [file]** / **git restore [file]** <br>
> 用暫存區(或上一次 commit)的內容**覆蓋**工作目錄的檔案 <br>
> ⚠️ 會清掉工作目錄裡**還沒 add** 的修改, 很危險, 用之前要想清楚

> **git checkout HEAD -- [file]** / **git restore --source=HEAD [file]** <br>
> 用上一次 commit 的內容覆蓋工作目錄, 連暫存區的變更也可能一併丟掉 <br>
> ⚠️ 同樣極具危險性

<br><br>


## 一個簡單例子

> 假設你修改了 `file.txt`: <br>
> 1. **工作目錄** — 存檔後, `git status` 會顯示 modified <br>
> 2. **暫存區** — `git add file.txt` 後, 變成 staged <br>
> 3. **儲存庫** — `git commit -m "Update file.txt"` 後, 這個版本就留在 `.git` 裡了 <br>
> 4. **遠端** — `git push` 才把本地 commit 送到 GitHub（見 2.5）
